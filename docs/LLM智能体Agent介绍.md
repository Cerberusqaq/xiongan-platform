# LLM 协同管控智能体（Traffic Copilot）介绍

> 赛道 C 补充要求：**大语言模型与多智能体强化学习融合**。本智能体即该要求的落地实现——
> 一个能"看懂态势、说出建议、动手调控"的自然语言交通管控助手，本地免费模型即可运行。

---

## 1. 定位：两级架构中的"大脑"

本平台采用 **LLM 高层协调 + MAPPO 路口执行** 的两级架构，正好对应赛题中"LLM + MARL"的融合：

```
┌─────────────────────────────────────────────────────────────┐
│                      用户 / 前端（自然语言）                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ "东侧拥堵，怎么办？"
                            ▼
┌─────────────────────────────────────────────────────────────┐
│              Traffic Copilot（LLM 智能体，高层协调）           │
│   看态势 ──► 决定调哪个工具 ──► 执行 ──► 检查结果 ──► 总结      │
└───────┬──────────────────────────────────────────┬──────────┘
        │ 工具调用（文本 JSON 协议）                  │
        ▼                                            ▼
┌──────────────────────┐              ┌──────────────────────────┐
│   感知类工具           │              │   行动类工具              │
│ 全局指标 / 路口相位 /   │              │ 路径规划 / 注入事件 /     │
│ 边级路况 / 事件列表    │              │ 调参 / 切模式 / 报告      │
└──────────────────────┘              └──────────────────────────┘
        │                                            │
        ▼                                            ▼
┌─────────────────────────────────────────────────────────────┐
│              平台既有能力（低层执行，已交付）                    │
│   MAPPO（强化学习路口控制）/ SCOOT（规则自适应）/ SUMO 仿真引擎    │
└─────────────────────────────────────────────────────────────┘
```

- **LLM 管"决策"**：面向人类用户，负责理解意图、分析态势、编排动作、给出可读解释；
- **MAPPO 管"执行"**：面向路口，毫秒级响应车流变化，自动决策每个路口的绿灯配时；
- 两者通过 **9 个工具** 解耦——LLM 不会直接碰仿真内部状态，只能通过工具白名单操作平台。

---

## 2. 为什么它是个"亮点"

| 特性 | 说明 |
|---|---|
| **免费离线** | 默认本地 Ollama + Qwen2.5:3b，零 API 费用、断网可用；也可一行环境变量切换任意 OpenAI 兼容大模型 |
| **真实执行，不是脚本演示** | 所有工具调用都真正作用于正在运行的 SUMO 仿真（改信号配时、注入事故车流、切控制模式都能在仿真里看到效果） |
| **安全护栏** | 工具白名单 + 参数范围校验，LLM 输出越界会被拦截并反馈，模型自动纠正（实测过） |
| **任意路网可用** | 路径规划用 Dijkstra 在实时路网上动态算，不依赖预训练路线；配合路网无关 MAPPO 权重，换路网零成本 |
| **小模型友好** | 用文本 JSON 协议（不依赖 function calling），1.5B/3B 小模型也能稳定跑通 ReAct 循环 |

## 3. 系统结构（代码地图）

全部代码在 `backend/app/agent/` 下，共 4 个文件、约 400 行：

| 文件 | 职责 | 关键内容 |
|---|---|---|
| `app/agent/llm.py` | LLM 客户端工厂 | `make_client()` → (OpenAI 兼容客户端, 模型名)；读环境变量 `LLM_BASE_URL / LLM_MODEL / LLM_API_KEY` |
| `app/agent/tools.py` | 工具定义 + 执行器 | `TOOL_SCHEMAS`（9 个工具的 JSON Schema）+ `execute_tool()`（白名单校验→执行）+ `_safe_params()`（参数范围校验）+ `_dijkstra()`（路径规划算法） |
| `app/agent/agent.py` | 智能体主循环 | `SYSTEM_PROMPT`（角色 + 工具参数文档 + few-shot 示例）、`_parse_action()`（括号配对 JSON 解析）、`run_agent()`（ReAct 循环：≤4 步）、`agent_status()` |
| `app/api/agent.py` | HTTP 接入 | `POST /api/v1/agent/chat`（普通 `def`，FastAPI 线程池执行，不阻塞事件循环）、`GET /api/v1/agent/status` |

平台侧集成点（不属 agent 目录，但构成完整闭环）：

| 位置 | 作用 |
|---|---|
| `app/main.py` | 模块末尾 `app = create_app()`，使 `uvicorn app.main:app` 可直接启动 |
| `scripts/agent_demo.py` | 一键演示：启动雄安仿真 → 注入突发车流 → 三个场景自然语言对话 |
| `e2e_agent.py` | 端到端回归：启动仿真 → agent 路径规划 → 停止仿真（UTF-8 客户端） |

## 4. 工作流程（ReAct 循环）

智能体不是一个"一问一答"的聊天机器人，而是一个 **思考-行动-观察** 循环：

```
用户输入
   │
   ▼
┌─────────────────────────────── 循环（最多 MAX_STEPS=4 步）──────────────┐
│  ① LLM 产出：要么是工具 JSON，要么是最终回复                             │
│      {"tool": "plan_route", "args": {"from_edge": "E21_1", "to_edge": "E9_19"}}  │
│  ② _parse_action 括号配对解析（兼容代码块包裹、嵌套 args）               │
│  ③ 工具名不在白名单？→ 回填"工具不存在，可用：..."，让模型重选（幻觉纠正）  │
│  ④ 连续 2 次重复同一工具 → 提示"已无新信息，直接总结"                     │
│  ⑤ execute_tool：_safe_params 范围校验 → 真实执行 → 结果回填给 LLM        │
│  ⑥ LLM 基于结果继续，直到输出自然语言回复或步数耗尽                        │
└──────────────────────────────────────────────────────────────┘
   │
   ▼
达到步数上限 → 强制注入"请基于以上所有工具结果给出最终中文总结"
   │
   ▼
最终中文回复 + 完整工具调用日志（tool / args / result）返回给前端
```

**协议选择说明**：早期实测发现 Ollama 0.23 的 function calling 参数（tools）有缺陷（`tool_calls` 恒为 None），因此改用**文本 JSON 协议**——LLM 直接在正文输出 JSON。好处：兼容小模型、兼容旧版 Ollama、也兼容任意 OpenAI 兼容 API，且日志天然可读。

## 5. 工具清单（9 个 Skills）

工具分三类：**感知**（读数据）、**行动**（改状态）、**报告**（汇总输出）。全部映射到平台已有能力，LLM 无需了解仿真内部。

### 5.1 感知类

| 工具 | 参数 | 作用 | 对应平台能力 |
|---|---|---|---|
| `get_network_status` | 无 | 全局实时指标：在网车辆 / 平均速度 / 平均等待 / 平均排队 | `/metrics/realtime` |
| `get_tls_status` | `tls_id` | 某信号路口当前相位、相位时长、排队情况 | 引擎 `get_tls_state` |
| `get_edge_status` | `edge_id` | 某条道路实时状态：车辆数 / 平均速度 / 占有率 / 限速（驾驶建议用） | 引擎 `get_edge_stats` |
| `list_events` | 无 | 已注入的扰动事件（施工 / 突发车流 / 事故） | `/events/list` |

### 5.2 行动类

| 工具 | 参数 | 作用 | 对应平台能力 |
|---|---|---|---|
| `plan_route` ⭐ | `from_edge`, `to_edge`（兼容 `start/end`、`from/to` 别名） | **Dijkstra 最优路径**（按实时旅行时间加权），返回建议路线边序列 + 预计行程时间 | 引擎 `get_edge_successors` 实时路网图 |
| `inject_event` | `event_type`(construction/large_event/accident), `edge_ids`, `vehicles` | 注入扰动：施工限速 / 突发车流 / 事故限速 | `/events/inject` |
| `set_params` | `min_green`(0–20), `max_green`(15–90), `switch_clearance`(5–20) | 调整方案二控制器参数（MAPPO/SCOOT 共用） | 方案二 `set_params` |
| `switch_mode` | `mode`(mappo/scoot) | 切换方案二控制器：AI 强化学习 / 规则自适应 | 方案二 `switch_to_*` |

### 5.3 报告类

| 工具 | 参数 | 作用 |
|---|---|---|
| `generate_report` | 无 | 汇总全局指标生成 Markdown 态势报告（含累计到达、活跃事件） |

### 5.4 plan_route 详解（本次新增的"驾驶建议"能力）

- **算法**：Dijkstra 最短路，边权 = 该边的实时旅行时间（无数据时按 1s 兜底），在**当前实时路网图**上动态计算；
- **特点**：不依赖预训练路线、不依赖特定路网——换任何路网都能规划，这正是"驾驶建议中可以规划路径"的实现；
- **实测**（雄安 base_network，80 边）：`"从 E21_1 去 E9_19"` →
  `plan_route(from_edge=E21_1, to_edge=E9_19)` 返回
  `["E21_1","E1_16","E16_13","E13_11","E11_9","E9_19"]`，预计 78 秒；
- **兼容性**：小模型常见参数名（`start`/`end`/`from`/`to`）均自动归一化。

## 6. 安全护栏（防 LLM 乱来）

LLM 输出**先校验、后执行**，这是交付给任意前端的前提：

1. **工具白名单**：只能调 `TOOL_SCHEMAS` 里声明的 9 个工具，幻觉出不存在的工具 → 回填纠正让模型重选；
2. **参数范围校验**（`_safe_params`）：枚举值白名单（如 `mode ∈ {mappo, scoot}`）+ 数值上下限（如 `switch_clearance` 下限 5）。越界返回 `{"ok": false, "message": "参数校验失败: ..."}`，模型看到反馈后自行纠正；
   > 实测：LLM 曾提交 `switch_clearance=2` → 被拒（低于下限 5）→ 模型自动改为 `min_green=5, max_green=30` → 通过并真实生效。
3. **无会话保护**：未启动仿真时，`/agent/chat` 直接返回"请先启动仿真"提示，不进入循环；
4. **循环保险**：MAX_STEPS=4 上限 + 连续重复动作检测，防止模型无限转圈；
5. **故障隔离**：LLM 调用异常（Ollama 未启动等）返回明确错误信息，不拖垮平台。

## 7. 与 MAPPO 的分工（融合点）

| 维度 | LLM（Traffic Copilot） | MAPPO |
|---|---|---|
| 频率 | 低频（秒级，人机对话驱动） | 高频（仿真步级，路口实时决策） |
| 视野 | 全局：理解语义、跨区域协调 | 局部：单路口状态→最优绿灯动作 |
| 输入 | 自然语言 + 工具返回的聚合指标 | 18/31 维数值观测 |
| 输出 | 中文建议、编排工具动作 | 信号相位动作（保持/切换） |
| 职责 | 应急响应、驾驶咨询、全局巡检、生成报告 | 常态路口信号优化 |

一句话：**LLM 决定"干什么"，MAPPO 决定"怎么把灯调好"**。二者经方案二的 `set_params / switch_mode` 等接口天然打通。

## 8. 部署与配置

### 8.1 模型（免费）

```bash
# 安装 Ollama 后拉取模型（已下载）
ollama pull qwen2.5:3b        # 1.9 GB，推荐（答辩稳定）
ollama pull qwen2.5:1.5b      # 986 MB，轻量备选
```

> **新机器部署**（答辩/交付机没有模型时）：`scripts/setup_ollama.bat` 一键完成
> "检查 Ollama → 拉取 qwen2.5:3b → 拉取 qwen2.5:1.5b"。
> 说明：LLM 模型本体（约 1.9 GB）由 Ollama 本地管理，**不随代码包分发**，
> 交付包内只有 agent 代码与配置，目标机执行上述命令即可联网获取（一次即可，之后离线可用）。

### 8.2 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | 后端预设：`ollama`（本地免费离线）/ `zhipu`（智谱免费 API，需联网） |
| `LLM_BASE_URL` | 按预设 | 显式设置时覆盖预设（任意 OpenAI 兼容端点） |
| `LLM_MODEL` | 按预设 | 显式设置时覆盖预设（如 `glm-4-flash`） |
| `LLM_API_KEY` | 按预设 | 显式设置时覆盖预设；**智谱预设留空占位**，填入真实密钥即可用 |

**预设速查**：

| LLM_PROVIDER | base_url | model | api_key | 场景 |
|---|---|---|---|---|
| `ollama`（默认） | `http://localhost:11434/v1` | `qwen2.5:3b` | `ollama` | 离线保底，答辩首选 |
| `zhipu` | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` | **留空，需填写** | 免费云端 API，联网即可 |

**切到智谱（三步）**：

```bat
set LLM_PROVIDER=zhipu
set LLM_API_KEY=sk-在open.bigmodel.cn申请的密钥
python scripts/test_llm_api.py        # 自检：打印配置 + 真实调用验证连通
```

> 也可把三项写进 `backend/.env`（`llm.py` 自动读取，真实环境变量优先）。
> 未填密钥时 agent 不会崩溃：`/agent/status` 返回 `api_key_configured: false`，
> 对话返回 401 的明确报错（实测：智谱端点返回"令牌已过期或验证不正确"）。
> **已用真实密钥全链路实测通过**（见 §9）。

### 8.3 启动与使用

```bash
cd backend
set LLM_MODEL=qwen2.5:3b
python -m uvicorn app.main:app --port 8000        # 启动后端
python scripts/agent_demo.py                      # 一键演示（三场景）
# 或直接调 API：
#   POST /api/v1/agent/chat {"message": "路况如何？"}          → {reply, tool_calls}
#   GET  /api/v1/agent/status                                  → {model, tools, max_steps}
```

三个演示场景（`agent_demo.py`）：

| 场景 | 指令示例 | 实测行为 |
|---|---|---|
| ①突发事件应急响应 | "检测到 E21_1 附近突发车流，请分析现状并给出应急调控建议" | 读全局/事件 → 分析 → 执行注入/切模式/调参 → 中文总结 |
| ②交通咨询/驾驶建议 | "我想从 E21_1 去 E9_19，请规划最优路径并给出驾驶建议" | plan_route 真实返回路径 + 预计时间 → 驾驶建议 |
| ③全局协调建议 | "请巡检全局路网，如发现拥堵区域请给出协调建议并执行" | 读全局指标 → 定位拥堵 → 调参/切模式 → 报告 |

## 9. 实测记录（诚实说明）

**通过项**：

- ✅ 三场景全链路真实执行（工具结果可在仿真中观察到）；
- ✅ E2E 回归通过：启动仿真 → `plan_route` 返回真实路径（78 s）→ 停仿真；
- ✅ 护栏实测：非法参数被拒并自动纠正；
- ✅ **智谱 glm-4-flash 全链路实测通过（2026-08，真实密钥）**：
  `test_llm_api.py` 连通 OK；E2E 中一次调用即完成路径规划并直接总结
  （"建议路线 E21_1 → E1_16 → E16_13 → E13_11 → E11_9 → E9_19，预计约 78 秒…"）；
  三场景演示全过（get_edge_status / get_network_status / plan_route / generate_report 均正确），
  表现稳定且总结质量不输本地 qwen2.5:3b。
- ✅ qwen2.5:3b 全程稳定；qwen2.5:1.5b 可用但细节偶有不稳（已备注）。

**已知局限**：

- ⚠️ 小模型在 4 步工具上限耗尽后，强制总结有时偏重全局态势、对具体工具结果（如路径）着墨不多——路径数据本身完整，只是总结侧重问题；如答辩需要可提高 MAX_STEPS 或加"plan_route 成功后直接输出路线"的提示；
- ⚠️ 工具结果为文本回填（截断 400 字符），超大路网的完整巡检信息可能截断；
- ⚠️ 规划基于实时旅行时间（仿真内数据），未叠加路况预测/历史先验。
